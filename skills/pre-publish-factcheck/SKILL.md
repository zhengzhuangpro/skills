# Pre-publish Factcheck（发文前对账）

## 适用场景

用户要把一篇介绍某个本地项目的文章（公众号、博客、发布稿）发出去，文章里写了产品的功能、数据、操作路径。发文前做一轮「文章 vs 代码」的事实对账，避免超卖、失实、图文不一致被读者戳穿。

## 指令正文

### 1. 提取声明清单

通读文章，把所有可验证的声明列出来，分四类：

- **功能声明**：带能力词的句子（支持 / 可设定 / 自动 / 会提醒……）
- **数据声明**：用户数、上线时长、收入等
- **操作路径**：让读者去某 App 某菜单操作的步骤
- **名称与图注**：产品名、功能名、每张配图的图注

### 2. 代码调研

派只读探索代理（或自查）进项目仓库，拿文件级证据（文件路径 + 关键内容）：

- README 里写的规划和定价**不算已实现**，以代码为准；无对应实现、无功能入口、写死的默认值，都算「没有」
- 硬编码检查：声称「可设定」的功能，看设置入口是否存在，还是只是一个写死的常量
- 名称核对：文章里的产品名 vs 代码里实际展示的名字。全称/简称可能都合法，问用户注册名是哪个，以注册名为准统一

### 3. 三色对账

每条声明给一个结论：

- ✅ **属实**：保留
- ⚠️ **超卖/失实**：改文。能力词降级——「可设定」→「内置」、「自动识别」→「自带」；宁可少说，不可多说
- ❓ **代码查不出**（用户数、收入等运营数据）：列出来问用户拿真实数字，**不猜、不编**。精确数字（1,282）比约数（一千多）更可信，并注明口径（如「累计」）

### 4. 渠道路径核查

文章让读者操作的具体菜单路径必须真实存在。第三方 App 的设置项不确定就查证；查不到就改成模糊但正确的表述（如「支付设置里的自动续费协议」）。注意：第三方 App 的账单筛选类目往往没有你想的那个选项，别想当然。

### 5. 配图核查（有图时）

用视觉分析逐字提取每张图的文字，检查：

- **错别字**：AI 生成图高发句首多字、重复词
- **图注与图内容对应**：图注提到的元素，图里必须真的有
- **图文话术同步**：正文改过的说法，图里的旧 slogan / 卖点文案要跟着改；图是外部工具出的，就把需要重出图的地方列给用户
- **图内 UI 与真实 App 一致**：筛选 tab 文案、产品名、演示数据是否与代码一致
- **真实截图 > 精修图**：占位数据（环比 0.0%、上月 ¥0.00、凑数的坐标轴刻度）经不起细看，能换真图就建议换

### 6. 去 AI 味检查表

- 破折号全文 **≤1 个**，留给最关键的揭底句；其余改句号/逗号/冒号
- 「于是：」→「于是，」；删「方方面面」这类公文填充词
- 「麻烦在于」等翻译腔改口语（「麻烦的是」）
- 「把 A 变成 B」句式、运营黑话（回访、赋能、抓手）改朴素说法
- 双 jargon 连用（如「归一化」+「口径」）降为一个或换白话
- 人味短语（口语四连、生活化比喻）保留不动

### 7. 定稿同步（用户在外部编辑器改过时）

- diff 编辑器版和本地底稿，把用户的编辑决定同步进底稿
- **绑定删句检查**：删一句话前查有没有别的句子依赖它（「毕竟/因为」的指代、首尾呼应、身份铺垫），要么一起删，要么恢复
- 标题、开头钩子、结尾引语三者呼应核对
- 最后输出一份「发布后台还需修改」清单（编辑器侧笔误、待换的图）给用户

### 输出格式

对账结果用表格：声明 | 结论（属实/超卖/查不出）| 证据或问题 | 建议。修文只改失实和 AI 味；标题选型、开头钩子这类编辑判断给选项让用户拍板，不代决。
